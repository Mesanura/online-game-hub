# 产品目标与范围

本文定义当前用户体验、能力和非目标。阶段状态见 [路线图](./ROADMAP.md)，游戏规则与支持版本见 [游戏索引](../games/README.md)，技术职责见 [系统架构](./ARCHITECTURE.md)。

## 产品定位

Online Game Hub 是多人在线网页小游戏平台。用户从统一目录选择游戏，通过私人房间码或邀请链接一起游玩。当前覆盖双人棋牌、2–6 人中国跳棋，以及乒乓对战、火柴人羽毛球和 2–8 人坦克迷战。

平台统一提供身份、房间、稳定席位、准备、重连和比赛记录；每款游戏独立定义规则、逐局设置与画面。浏览器只提交操作意图，服务器裁定结果。已记录的比赛可按对应规则版本确定性重建。

游戏规则可以基于公共领域或合法授权内容；名称、界面、美术、音乐、图标和文案必须原创或具备明确授权，不复制其他产品的受保护表达。

## 当前能力

- 游客无需注册即可创建、加入、游玩和重连。
- 房间通过邀请码分享；参与者完成游戏设置并分别准备后开局。
- 同一房间支持多轮比赛、平台投降确认、房主关闭和非房主离开。
- 用户名与密码账户提供可撤销登录态、个人显示名和私有比赛历史。
- 棋牌提供账户私有回放；三款实时游戏目前只保留服务端记录和账户战绩。
- 游戏画面使用独立 Surface，支持响应式布局、键盘操作和相应触屏输入。

## 用户流程

### 创建与准备

1. 从首页进入游戏入口，创建私人房间或输入房间码加入。
2. 房主复制邀请链接；复制控件提供进行中、成功、失败和手动复制后备。
   等待页按席位展示玩家头像、显示名、本人/房主标记及在线和准备状态；空席位显示等待占位，已加入但断线的玩家保留资料并显示暂时离线。手机布局也显示头像，长显示名自动换行。
3. 参与者通过游戏自己的 Setup 选择规则、人数、顺序或阵营；平台不假定每个游戏都有先手设置。
4. Setup 选中的全部参与者到齐、在线、分别准备且设置有效后，服务器开始新一局。

入口、等待和对局分别对应 `/games/{gameId}`、`/games/{gameId}/rooms/{roomCode}` 和其 `/play` 子路由，均可刷新或通过链接进入。旧 `?roomCode=` 邀请继续规范化到房间路由；页面阶段由服务器 lifecycle 决定。

从入口创建或加入房间时保留入口的浏览器历史；等待与对局之间自动切换不堆叠历史。后退返回入口会主动离开旧房间、清空房间码与邀请状态，随后可以创建或加入新房间；若当前对局仍在进行，离开前须确认，取消则保留连接并返回对局。

### 对局与重新开局

玩家只看到自己有权查看的服务器视图。回合制游戏提交 Action，实时游戏提交控制 Input；合法性、计分、排名和终局均由服务器判断。

结束后保留最终画面，右侧非模态 HUD 显示游戏提供的纯文本结果摘要、逐玩家“重新对局”确认和“调整设置”。下一轮默认复用上一局完整最终设置，包括 Config、参与者、实际顺序和阵营；随机顺序不自动重抽。每位玩家仍须分别重新准备，任一 accepted 设置变更会清空全部确认。新一轮拥有独立 State、seed、Match 和 replay。

平台提供投降二次确认，游戏决定投降结果。房主可以关闭房间，非房主可以主动离开；终止 active 对局前必须确认。网络离开或房间关闭产生的平台 `abandoned` 状态不伪装成游戏胜负。首局尚未开始的房间不创建 Match，也不进入历史。

以上是当前 V6 体验；存量 V5 的即时重开等兼容行为仅按 [网络协议](./NETWORK_PROTOCOL.md) 保留。

### 舞台与可访问性

游戏舞台占满可用空间。平台 HUD 是默认收起的覆盖式抽屉，不挤压舞台；左上角为抽屉开关，右下角为独立全屏开关，连接详情放在抽屉与辅助技术状态中。全屏不可用时降级为 `100dvh` focus mode。

比分、棋子、阵营、回合、排名和结果表现由 Surface 提供。大型棋盘的滚动、缩放以及 canvas 布局也由各 Surface 负责；移动端操作目标至少 44px，支持可见焦点、必要的语义状态和 reduced motion。Surface 加载或校验失败时显示可重试错误，不提交操作。

### 断线与回收

刷新或短暂断线后，原身份默认有 60 秒宽限期恢复稳定席位；重连取得当前完整视图。超过宽限期关闭房间，active 比赛标记 abandoned。completed 房间不接纳新参与者，5 分钟未开始下一轮会被回收。

当前为单 Game Server 实例。服务重启不会恢复 live room、待开局设置或权威 State；已持久化的比赛与记录保留，遗留 active archive 会标记 abandoned。

## 账户、资料与历史

### 身份与比赛归属

用户名规范化为小写 ASCII，符合 `[a-z0-9_]{3,24}` 且唯一；密码长度 8–128。登录态有效期为 30 天，可通过退出撤销。登录、注册、退出或账户 session 失效会轮换访客 session。

游客可以完整游玩，但没有历史或回放读取入口。只有在 Round 开始时已绑定到账户的席位才记录账户归属；注册、登录或归档重试不会认领此前的游客比赛。同一 live seat 不能切换账户，也不能在游客与账户身份之间转换；后续 Round 沿用席位身份。房间中执行身份变更前，页面须说明离开后会失去席位并要求确认。

历史最多返回当前账户最近 50 条安全比赛 metadata，不开放其他账户或公开比赛列表。回放仅对参赛账户开放，并受 exact 游戏版本能力约束：

| 游戏能力          | 账户体验                                            |
| ----------------- | --------------------------------------------------- |
| `player-playback` | 已完成且可验证的比赛可逐帧查看、播放/暂停和拖动进度 |
| `record-only`     | 保留战绩，服务器继续保存并验证记录，不提供播放入口  |

当前没有使用 `none` 的游戏。回放不提供下载、公开分享或观战，浏览器只接收服务端投影帧。权限和记录格式见 [Replay 设计](./REPLAY_DESIGN.md)。

### 显示名与头像菜单

游客显示名默认为“游客”，可在当前浏览器修改并保存到固定 `localStorage` key；账户资料保存到 PostgreSQL，可跨设备读取。登录或退出不会迁移、认领或覆盖游客资料。右上角菜单和等待页使用同一套显示名与头像规则；资料保存后同步给同房间玩家，刷新或重连时读取最新资料。改名不切换席位身份、不清空准备状态，也不改变已归档比赛或 replay。传递与兼容契约见 [网络协议](./NETWORK_PROTOCOL.md#43-http-ticket-api)。

显示名输入最多 512 个 UTF-16 code unit，再执行 NFC 规范化和首尾空白裁剪；规范化后长度为 1–24 个 Unicode grapheme cluster，不得为空或含控制字符。头像不接受图片上传，按以下规则生成：

- 首位为汉字、完整 emoji 或其他非 ASCII 字母数字时，取首位。
- 首位为 ASCII 字母数字但第二位不是时，取首位；否则通常取前两位并转大写。
- 数字开头的连续 ASCII 字母数字前缀若含至少两个数字，取其中前两个数字。例如 `1a2b🐷你好` → `12`、`1你好2` → `1`、`🐷a` → `🐷`。

使用 `Intl.Segmenter` 保持 ZWJ 和旗帜 emoji 完整。头像菜单支持悬停、聚焦、点击、Escape 与外部点击关闭；游客操作为登录/注册，账户操作为历史对局/账号设置/退出。

## 当前非目标

- 公开房间大厅、自动匹配、排行榜、Rating、赛季和好友系统。
- 邮箱验证、找回密码、管理员重置、OAuth 和通用账户删除产品。
- 公开历史、公开回放、下载、分享链接、独立观战及隐藏信息回放权限产品。
- active room 跨进程恢复、checkpoint、Redis 协调、多 Game Server、跨区域部署、Kubernetes 或微服务拆分。
- 为未提出的游戏预建脚本系统、通用 ECS、物理模板、客户端预测或回滚框架。

这些能力只有在明确需求或运行证据出现后才单独立项。现有游戏维护不自动扩大平台范围。

## 成功标准

用户能够从目录完成邀请、准备、对局、短暂断线恢复和同房间下一轮；账户能查看属于自己的比赛。新游戏可在自己的 Core、Setup 和 Surface 中实现，平台不理解其胜负或合法动作，旧记录仍能由对应版本重建。工程验收按 [测试策略](./TESTING.md) 执行。
